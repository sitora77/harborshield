# 单证实验：它能验证什么，不能验证什么

## 先从公开示例开始

运行本地应用后，打开 **Trade-document lab**。默认展示的是完全构造的发票、
装箱单、投保申请，没有公司或客户资料。v0.4 的默认单证从当前业务案例的同一订单生成，
并带有订单输入、SHA-256 输入摘要和方案筛选结论。修改业务案例的资金或延误假设后，
签署的上下文也会变化；它不会把利率或融资上限当成发票金额。下载示例 JSON 后，可用文本编辑器
修改，再上传检查。应用代码不保存上传文件，也不向第三方发送它们。
这里只支持结构化 JSON，不会识别扫描件、图片、PDF 或任意 Excel 文件。

网页案例中的单证表是已执行测试的静态快照；真正上传检查及签名实验在本地应用。

## 试三个错误

1. 把发票的 `total_value` 从 150000 改成 150001：程序应发现合计与明细不一致，
   以及投保申请货值与发票不一致。
2. 把装箱单的数量从 5000 改成 4999：程序应提示 SKU 数量不一致。
3. 把发运日期改为 2024-07-01：它超出示例申请中的保障时间窗口，应触发提示。

投保申请里显式设置了 1.1 的估值倍数，申请保险金额为 165000。因此不能把
“保险金额不等于发票金额”一律当成错误。这个倍数只是示例输入，不是对任何
保险合同或贸易条款的法律解释。日期检查也不等于判定实际是否承保。

重复发票编号检查需要另行提供已知编号登记表；当前本地界面没有登记表入口，
Python 接口支持这个功能。重复编号只提示可能重复，不证明融资欺诈。

## 数字签名实验

签署的是当前通过一致性检查的构造资料，或你上传后通过检查的 JSON 演示资料。
上传资料不一致或格式错误时，程序会阻止签署，不会退回默认订单并显示成功。
输入摘要只能绑定内容；一致性规则不验证上传文件里额外业务上下文是否真实或计算正确。
即使所有资料相互一致，也不能证明原始交易真实。

切换下拉菜单，观察三个结果：

| 测试 | 签名有效 | 与单独提供的原始公钥一致 | 证明真实交易 |
|---|---|---|---|
| 原始签名示例 | 是 | 是 | 否 |
| 签名后更改金额 | 否 | 否 | 否 |
| 换一把密钥重新签名 | 是 | 否 | 否 |

最后一行很重要：任何人都能生成密钥，并用自己的密钥签一份文件。
所以不能因为“文件自带的公钥验证通过”，就相信它来自某家真实银行。
必须另有可信渠道提供预期公钥，并建立它与真实机构身份的关系。
我们的示例只是临时教学密钥，没有建立真实机构身份。

程序使用 cryptography 库中的 Ed25519，不自行实现密码学算法。签名包含
正文、算法和示例签发者字段。密钥在内存里随机生成，私钥不写入仓库或下载文件。
JSON 编码是本项目自己的约定，不是 TradeTrust、W3C 凭证或 RFC 8785 标准。

## 如何下载再验证

1. 下载原始示例签名文件。
2. 单独下载示例公钥，保留它作为此前获得的教学信任锚。
3. 在“Verify a saved DEMO envelope”上传签名文件，并填入保存的公钥。
4. 原文件应验证通过；更改正文后应失败。重新开一个会话会生成新密钥，
   所以验证旧文件时使用此前保存的公钥，不要使用新会话的密钥。

公钥不是秘密，但它的来源需要可信。不要从未知文件中复制其公钥，
再把它说成经过独立确认的机构身份。

## 真实业务接入还缺什么

需要得到授权的数据和可靠的身份绑定，还要处理签发者注册、撤销、权限、
重复融资登记、审计、格式互通和业务验收。电子提单还涉及货权和法律效力。
这些没有实现。代码里的规则通过不代表货物存在、保单成立、贷款获批或
交易唯一，也不意味着本项目与银行、保险公司或 TradeTrust 有合作。

参考：[TradeTrust 2023 年真实交易说明](https://www.tradetrust.io/happenings-and-resources/press-release-singapore-india-kick-off-interoperable-ebills-of-lading-for-trade-finance/)、
[TrustVC 开源实现](https://github.com/TrustVC/trustvc)、
[cryptography 46.0.7 官方文档](https://cryptography.io/en/46.0.7/hazmat/primitives/asymmetric/ed25519/)。
